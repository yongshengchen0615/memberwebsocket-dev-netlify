# Project #5｜敏捷式開發規範（Scrumban）

> 適用會員、預約、LINE、點數／票券、管理端及漸進架構整理。採 Scrum 目標與回顧、Kanban 持續交付，不需要虛構完整 Scrum 團隊。補充 AGENTS.md 和 DEVELOPMENT_GUARDRAILS.md；若衝突，以資料安全、原功能防退化和發布 Gate 為準。
>
> 本文件為工作約定；GitHub Ruleset / Required Checks 的技術強制須另以實際設定與拒絕測試驗證。本規範不修改正式環境、Issue Status 或 Projects 自訂欄位。

## 1. 目標、角色與產品待辦（Backlog）

- 以業務價值和可驗收的小增量排序，不以 Issue 數量、程式碼行數或 Story Points 當績效。
- 專案維護者（人）負責產品優先級、驗收核可與發布授權；AI Agent／開發者負責提案、實作、測試和證據，不能代替授權。
- Epic 用於追蹤大目標，Story／Bug 必須可獨立驗收，Task 只保留必要拆解；不因 Epic 的部分子卡通過就將整個 Epic 標完成。
- 依 #39 優先完成可驗收功能；必要安全與測試隨功能執行，獨立架構/治理改版依價值另排，不使用固定雙軌工時比例。
- 不自動新增 Sprint、Iteration、Story Points 欄位；Project #5 欄位若不能讀取，以 Issue 本文記錄迭代目標，待權限恢復再設定。

## 2. 迭代節奏（建議一週）

1. **Backlog Refinement**：需求先補價值、影響、相依和驗收；重複卡整合，過大工作拆成可驗收切片。
2. **Sprint Planning**：預設每週一次，建議 15–30 分鐘或非同步。定義單一 Sprint Goal，選 1–2 個最有價值的可驗收成果及緩衝。未實際排程不得填虛構交期。
3. **Daily async**：有開發的工作日以 2–3 分鐘記錄「已完成且可驗證的證據／今天下一步／阻礙及決策」，無需強制開會。
4. **Sprint Review**：每週結束用 Demo、PR、CI、Preview 和業務驗收結果展示 Sprint Goal 是否達成，不以口頭完成代替證據。
5. **Retrospective**：每週記錄「保留什麼／改善什麼／下輪執行一個可驗證行動」，以追蹤卡承接改進。
6. **Carryover**：未達 DoD 的工作保持未完成，確認剩餘風險後重新排入 Backlog；不得因迭代結束就改成已完成。

週期可根據實際容量調整；時間盒是協作節奏，不等於放寬品質標準。

## 3. Definition of Ready（DoR）

每張新開發卡先進「規範確認」完成檢核，再進「準備開始」。該選項已建立且 main 同步已合併，原九項保留，共十項。六項 DoR 詳見 DEVELOPMENT_GUARDRAILS.md 第10節，至少具備：
- 使用者角色、商家歸屬、業務價值或可重現缺陷；明列不做範圍。
- Given／When／Then 驗收條件、受影響既有功能、適用的測試策略及相依工作。
- Priority、目標分支與負責人（或待分派標註），安全／資料／發布風險可判斷。
- 跨商家功能須分別定義 A 店／B 店、管理端 OA／會員端 OA 的授權、資料和 LINE 路由邊界。
- 不確定可先建立有時間限制的探索 Spike；Spike 以結論、風險或最小實驗為驗收，不等於完成產品功能。

## 4. WIP 上限與緊急插單

- **WIP 上限**：同時主動修改中的程式 PR 最多 2 個，以收斂功能交付為先。長期保留的 Draft 不計入主動 WIP，但必須註明等待原因和下一個檢查點。
- 同一共享 JS、Edge、SQL、CI 或資料契約遭不同 PR 修改時，先決定合併順序；第二條須更新基線 SHA、重跑測試。
- **P0 緊急插單規則**：可中斷 Sprint Goal，需記錄插單原因、被替換的工作、負責人、回退及驗收；P0 不能繞過 CI、正式授權或發布 Gate。
- 已阻塞的卡片記錄原因、持有人、解除條件和下次查核；解除後回到正確工作階段，不直接 Done。

## 5. 與 Project #5 十個 Status 對應

| Status | 敏捷意義與移動條件 |
|---|---|
| 待規劃 | Product Backlog；需求、優先級、依賴待釐清 |
| 規範確認 | 六項 DoR：需求/AC、基線、舊功能影響、資安、詳細測試計畫、交付/回復；具備才進準備開始 |
| 準備開始 | DoR 已滿足，排入工作或明確待辦 |
| 開發中 | 獨立分支、測試與最小可驗收程式增量 |
| 程式碼審查 | PR diff、風險、受影響功能及測試可供審查 |
| QA / E2E | 必要 CI、整合／安全負向、適用外部驗收 |
| 等待部署 | 同版 SHA、核准、資料庫相容性與回復方案 |
| 觀察中 | 已部署並執行 Smoke、健康與回歸觀察 |
| 已完成 | 全部適用 DoD 與必要證據完成 |
| 已阻塞 | 暫停例外；解除後返回原流程恰當狀態 |

使用原有 01 開發看板、02 工作清單、03 Roadmap、04 QA、05 風險、06 已阻塞、07 QA 與發布關卡。**不能把文件建議寫成已存在的 GitHub 欄位。**

## 6. Definition of Done（DoD）

Story／Bug 要成為已完成，必須依工作範圍達到以下條件：
1. AC 已驗收，包含正常、錯誤、空資料、邊界、角色與跨商家負向案例。
2. 原功能與相鄰模組回歸通過，最終候選 SHA 的必要 CI 有證據；failed、skipped、cancelled、pending 或未執行不得當成功。
3. PR 已完成適用的獨立 Code Review、資安與資料契約審查，不以移除測試、減弱斷言、增加 retry 取得假綠燈。
4. Issue／PR 記錄範圍、修改檔、測試命令與 run URL、SHA、回退及尚未驗收項；LINE Stub 不等於真人 LINE 驗證。
5. 若 Issue 本身要求正式發布，另需正式批准、Netlify Deploy ID、Supabase Edge／migration 相容和部署後 Smoke／觀察證據；**僅合併 PR 不等於發布或 Done**。
6. 純文件／治理變更以文件 AC 和治理測試驗收，不能為了滿足格式虛構 Production 發布。
7. 未達上述適用 DoD 時明確保持 QA、阻塞或其他對應階段；**不得因 Sprint 結束就標完成**。

## 7. 每週回顧及可量測指標

- 回顧 Sprint Goal 完成與否、已驗收交付物、未完成原因以及一項下週改善行動。
- 只量測可取得的 Lead Time、Cycle Time、Blocked Aging、完成工作數、CI 不穩定和正式缺陷；先建立基準，再做前後比較。
- 不以 Story Points、Velocity、Commit 次數或 AI 產碼行數作人員績效，無真實數據時一律標「待量測」。

## 8. Issue 精簡紀錄格式

- Sprint Goal：本輪要完成的業務結果
- 本輪範圍／非目標／依賴：關聯 Issues 與風險
- DoR：角色、商家範圍、AC、目標分支、負責人、測試
- Daily async：已證實結果／下一步／阻礙
- Sprint Review：AC → 同版 SHA／CI → Demo／Preview／發布（適用時）
- Retrospective：一項可測量的後續改善工作

看板已新增第十項並由 main 同步實際寫後讀回。正常順序為「待規劃 → 規範確認 → 準備開始 → 開發中 → 程式碼審查 → QA / E2E → 等待部署 → 觀察中 → 已完成」；已阻塞為例外。保護設定與後續每張功能卡的真實驗收分別判定。

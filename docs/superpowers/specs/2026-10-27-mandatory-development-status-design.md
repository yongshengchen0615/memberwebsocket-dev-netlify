# 規範確認與每次開發品質關卡

依據 #56 使用者已確認的規劃：新增「規範確認」，置於待規劃與準備開始之間；每次開發保護既有功能、驗證資安、小增量交付並詳細測試新功能。

## 方案與決定

沿用現有 PR #131 的風險與說明檢查，不另建治理平台。相較只加看板欄位，此方案可在 PR 實際產生不通過的檢查；相較重寫完整發布系統，它保留現有精確 SHA CI 與 Preview 管道。使用者「繼續」後，以本 session 直接實作。

## 邊界

- 開工 DoR：需求/AC、來源基線與環境、舊功能影響、資安邊界、測試計畫、回復。
- PR 內的文字檢查只驗證內容具備，不證明測試已執行或系統沒有漏洞。完整 CI、獨立審查、真實外部驗收及發布授權繼續適用。
- 必需欄位不可缺少、空白、使用範本待補值，亦不可藏在註解/程式碼範例或用重複標題造成歧義。普通說明文件無 runtime 影響時保留現有輕量例外。
- 保留原九個 Status、所有 Project items 及權限；新增後共十項。Status 程式另在 default branch main，須獨立 PR，與產品整合分支不互相覆寫。
- 新 Status 尚未在 Project 建立時，不合併要求十項的 main 同步修改；現有九項持續有效，DoR 在待規劃內先執行。
- 目標 Integrated-Marketing-Platform；不改產品/SQL/LINE/Supabase/Production。不放寬測試、授權或發布限制。

## 驗收

AC-FLOW-002：小型程式 PR 缺任何必需開工欄位，CLI 失敗；完整內容成功。註解、fence、重複標題與原始範本不可過關。

AC-FLOW-003/004/005：既有完整 CI 與獨立安全審查仍為交付條件。Required Checks/PR review/direct-push 禁止只有在 GitHub 真實設定並驗證後，才能宣稱強制。

AC-FLOW-001：main 的手動及 label 事件支援「規範確認」，原九項仍可移動，缺選項或回讀不符須失敗。實際 Project 變更需已登入且可編輯的介面，或具備相應能力的 connector。

AC-FLOW-006：敏捷以可驗收增量、主動 PR WIP≤2、每日非同步結果/下一步/阻礙與每輪回顧執行；完整測試不因迭代截止而略過。

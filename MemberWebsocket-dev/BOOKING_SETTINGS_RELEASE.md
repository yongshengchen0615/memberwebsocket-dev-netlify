# 預約設定、固定活動票券通知與模式偏好

## 行為

- 管理端可設定「必須預約主要技師才能成立預約」。規則以整筆預約為單位：開啟時至少一位服務對象須預約主要技師，否則無法成立預約；關閉時不必預約主要技師，仍可保留主要技師設定。新增設定預設開啟，沿用既有行為。
- 關閉後可選其他開放技師，也可全部選「現場安排」。Server 與資料庫仍驗證所選技師、重複指派、服務與時段衝突。新建、修改及管理端登記採用提交當下設定；既有預約不回寫，完成既有預約不追加主要技師要求。
- 點數與會員服務分鐘仍只計入主要技師服務項目；沒有主要技師服務的預約可完成，獎勵為零。無障礙收據登記若仍配置主要技師則沿用自動指派，否則使用現場安排。
- 固定活動票券模板可關閉 LINE 通知，或指定 Asia/Taipei 的 HH:mm。留空沿用發券後立即通知；指定時間早於實際發券時間時立即排入待送。既有每日發券排程為台北 00:05，00:00 設定不會讓通知早於發券。
- 修改通知時間重排未送出工作；停用取消待送工作。重新啟用只恢復因停用而取消的工作，送出前再次核對模板、會員綁定、會員資格與持有票券。已送出工作及既有 LINE retry key 不變。其餘預約通知沿用原規則。
- 預約頁首次使用一般模式；主動切換後在目前瀏覽器以 LINE 會員識別隔離保存偏好。忽略舊共用偏好，損壞值或儲存不可用時使用一般模式。會員辨識及偏好套用完成才顯示預約頁。切換僅改變顯示，不清除表單與收據草稿。

## 部署與回復

先套用 `20261006081433_booking_primary_requirement_fixed_notification_time.sql`，再部署 booking-group-api、booking-group-slots-api、booking-receipt-api、fixed-ticket-automation、scheduled-grant-messages，最後發布前端。

需要回復產品行為時，在管理端選擇一位開放主要技師並重新啟用必填；各固定票券通知時間清空即恢復立即通知，通知開關可保持原值。保留新增相容欄位及通知資格檢查，不刪除已有現場安排預約。若回復舊版程式，須先恢復以上設定，且保留新版發送資格檢查避免待送通知繞過停用設定。

## 驗證範圍

新增測試涵蓋兩支預約 API、PostgreSQL 真實函式、現場安排建立與完成、無障礙收據登記、通知跨午夜／改時間／停用／重啟／去重、service_role 權限、管理端儲存重載，以及桌機與手機深色模式偏好。

LINE 發送使用隔離的 mock transport；沒有向正式會員推播測試訊息。實際 LINE 接收仍需由授權測試收件人驗收。

本機驗證結果：672 項單元測試、100 個管理端 DOM 流程、6 項模式與無障礙整合測試、6 項 PostgreSQL 設定與通知測試通過；五支修改的 Edge Functions 已通過 Deno 型別檢查。本機 Chromium 啟動失敗，手機與桌機實際瀏覽器截圖證據須由 GitHub CI 補齊。
